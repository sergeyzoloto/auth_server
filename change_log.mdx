After changing the backup scripts, run the restore test for both instances. The backup tables and the monthly routine mention the `finance` instance.
- `docker compose exec -T` passes its stdin on to the container, so in a script fed to bash (for example over SSH) it can swallow the lines after it. `deploy/backup/restore-test.sh` (`q_prod`) and `deploy/backup/pg-backup.sh` (the `pg_isready` wait and `pg_dump`) now give it `</dev/null`; the other calls there read a dump file. The other scripts were already safe: `deploy/caddy-site.sh` wraps every `docker compose` call in `</dev/null`, `deploy/sync.sh` runs its only `exec -T` in an SSH command whose input is `/dev/null`, and plain `docker exec` without `-i` reads no input. The runbook's own `exec -T` lines (kcadm session cleanup, the restore steps and their rollback) got `</dev/null` too.
- `deploy/smoke-test.sh`: Keycloak 26.7.4 answers a wrong client secret with 401 `unauthorized_client` "Invalid client or Invalid client credentials" (not `invalid_client`, as the comment said), and the password grant of a client without direct access grants with 400 `unauthorized_client` "Client not allowed for direct access grants". The password-grant check accepted 400 or 401 with `unauthorized_client`, so it also passed with a wrong `CLIENT_SECRET`. Both negative checks now go through one helper that requires the exact HTTP status, error code and `error_description`. `PRODUCTION.md`, "Run the smoke test", says so and asks to compare the answers after a Keycloak upgrade.

D1.1: unique Keycloak upstream alias, validated site installs.

- Compose: Keycloak gets the network alias `auth-keycloak` on the stack's own network only, and the Caddyfile proxies to `auth-keycloak:8080` instead of `keycloak:8080`, so a container on `edge` named `keycloak` can no longer receive `auth.finance-nl.com`'s traffic. On `edge` the prefix `auth-` is reserved for this stack, and every other container is named with its project's prefix (`finance-…`). No Keycloak or realm setting changed.
- New `deploy/caddy-site.sh`, installed by `deploy/sync.sh` as `/usr/local/sbin/caddy-site`. `caddy-site install /root/finance.caddy` validates the deployed Caddyfile with the current site files and the candidate in a throwaway container of the running Caddy's image, with its environment and without network or volumes; only then does it put exactly the validated file live as `/opt/caddy-sites/finance.caddy` (root, mode 644) with an atomic rename and reload Caddy, and if the reload fails it restores the previous version (or removes the new file) and reloads again. `caddy-site remove finance` moves the file into a directory named by UTC time under `/root/caddy-sites-removed/` and reloads Caddy, putting the file back if Caddy rejects the configuration without it. Replaced versions are kept there too; the source file of an install stays where it is. Both refuse to act while the caddy container is down or still runs an older Caddyfile than `/opt/auth/Caddyfile`.
- `deploy/sync.sh`: before copying anything, also with `--dry-run`, it validates the new Caddyfile together with the files in `/opt/caddy-sites`, with the Caddy image and environment that the new compose file and the server's `.env` define (this needs `python3` on the server), and stops if Caddy would not start. After `docker compose up -d` it restarts caddy when the Caddyfile inside the container differs from `/opt/auth/Caddyfile`. The Caddyfile is a single-file mount and rsync replaces files by renaming, so until now a deploy that changed only the Caddyfile left Caddy on the old one, even through a reload. Both checks use one temporary directory on the server, which is removed on exit.
- `PRODUCTION.md`: "Hosting another project behind this Caddy" now installs and removes site files only with `caddy-site`, never by copying into `/opt/caddy-sites`, and states the naming rule for `edge`. The deploy description covers the new checks and the caddy restart, the undo procedure restarts caddy, and the Caddy and container notes mention `auth-keycloak`. README file tree updated.
- Verified locally with the pinned Caddy image: with Caddy on its own network and on an edge network, a decoy named `keycloak` on the edge network got none of the auth site's traffic, both with the production order of the networks and with the order reversed (5 of 5 requests reached the Keycloak stand-in each time, admin paths 403). A decoy named `auth-keycloak` with the order reversed did get it, which is the case the reserved prefix rules out. Every `caddy-site` path was run in a local compose project, and `sync.sh --dry-run` with a broken Caddyfile stopped before copying.
- Verified in production: a database backup before the deploy; Keycloak recreated with the alias (about 26 seconds of 502 and 503 while it started), caddy restarted by the new check, and the running configuration proxies to `auth-keycloak:8080`, which resolves to Keycloak only; smoke test 11 ok / 0 fail; admin console 403 over IPv6 from outside the allowlist and 200 from the allowlisted address. `caddy-site install` of a valid test site made it answer; a broken one was rejected and never appeared in `/opt/caddy-sites` (the directory's modification time did not change); a replacement that passed validation but failed at reload was rolled back to the previous version; `caddy-site remove` took the test site offline, and the test files were deleted. Stage 3: automated Postgres backups with restore test and laptop pull (audit P0-5).

- New `deploy/backup/pg-backup.sh`, installed on the server as `/usr/local/sbin/pg-backup`. One config file per database in `/etc/pg-backup/` (`auth.conf` for Keycloak). It runs `pg_dump -Fc` inside the database container over the local socket (no password), checks the archive with `pg_restore` (non-empty table of contents, and every data block reads back), renames it atomically to `auth-YYYY-MM-DDTHHMMZ.dump` in `/var/backups/pg/auth/`, deletes dumps older than 14 days while always keeping the newest 3, and writes a `last-success` status file. A failed run leaves no file and exits non-zero. Systemd template units `pg-backup@.service` and `pg-backup@.timer` (daily 02:30 UTC, `Persistent=true`, 10-minute random delay); `pg-backup@auth.timer` is enabled.
- New `deploy/backup/restore-test.sh` (`/usr/local/sbin/pg-restore-test`): restores the newest dump into a throwaway container of the production Postgres image (`--rm`, `--network none`, no ports, no volumes, data on tmpfs), compares the number of tables and the config's checks (realms, users and clients in `myapps`) with production in read-only transactions, removes the container and prints PASS or FAIL.
- New `deploy/backup/pull-backups.sh` with systemd user units `finance-nl-backup-pull.service` and `.timer` (daily 18:00 local time, `Persistent=true`): the laptop pulls `/var/backups/pg/` into `~/backups/finance-nl-server/` with rsync and a dedicated key, keeps 60 days, and warns with a desktop notification and a non-zero exit when the pull fails or a database's newest dump is older than 36 hours. The server's `authorized_keys` allows that key only `rrsync -ro /var/backups/pg/` with `restrict`; the previous file is kept as `/root/.ssh/authorized_keys.bak-2026-09-27`.
- New `deploy/backup/install.sh server|laptop` installs these pieces. `deploy/sync.sh` no longer copies `deploy/backup/` to `/opt/auth`.
- Backup directories are mode 700 and dumps mode 600, on the server and on the laptop.
- `PRODUCTION.md`: what the backups cover, and a runbook for running a backup, checking the timers, the restore test, restoring production from a dump (documented, not executed), adding the finance database and the laptop pull. README file tree updated.
- Verified: first backup 250,604 bytes; a failing dump leaves no file, and retention keeps the newest 3 (tested with temporary configs, removed afterwards); restore test PASS (100 tables, 2 realms, 1 user and 10 clients in `myapps`), and FAIL on a truncated dump; the pull key cannot open a shell, run other commands, write, leave `/var/backups/pg/` or forward ports; the first laptop pull matches the server's checksum; the SQL of the documented restore and rollback worked in a throwaway container. Keycloak used 539 MiB of its 1 GiB limit (53%), so the limit is unchanged.
